## 记录规则

1. **设计或技术方向改变：** 更新[开发方案](development-scheme.md)，并在实际发生当天的日志说明原因。
2. **待办、优先级或状态改变：** 更新[开发计划](development-plan.md)。完成状态要有相应日期日志支撑，不把计划事项写成已完成。
3. **每次实际工作：** 在 `plans/YYYY-MM-DD.md` 记录新增功能、修改/修复、决策、相关文件及**实际执行**的验证（命令、设备/视口、结果与未覆盖范围）。仅整理文档时明确说明没有代码功能新增。
4. **留存历史：** 日志保留当时事实；若后来被替换，在新的日期记录替代关系。已删除旧文档可写原文件名，链接只指向当前存在的文件。
5. **保持入口有效：** 新增日期日志时补充上方索引；移动或删除文档后检查本文及项目内 Markdown 的相对链接。

### 任务编号与 Git 追溯（必须执行）

- **任务编号：** [开发计划的任务台账](development-plan.md#3-任务台账唯一编号)为唯一编号来源；格式 `CAR-001`，按顺序递增、永久唯一。一个任务多日开发沿用同一编号，新增任务才分配新编号。
- **开始开发前：** 确认已有任务 ID、状态和验收条件；没有匹配项时在计划中建新 ID。设计变更同步修改开发方案，未来待办只写在开发计划。
- **结束开发时：** 当日 `plans/YYYY-MM-DD.md` 至少补全任务关联信息，并记录实际完成内容、涉及文件、验证过程、结果与限制；同日只维护一份日志。`CAR-XXX` 必须与计划中的编号一致。
- **Git 追溯：** 推荐提交标题采用 `feat(CAR-003): ...`、`fix(CAR-005): ...` 或 `docs(CAR-007): ...`。在任务日志中填入真实 commit SHA；尚未提交则明确填写“未提交”，不得编造 SHA 或假称已通过检查。创建提交后回填任务对应日期日志。
- **完成状态：** 根据已执行的验证在计划中更新任务状态及日志日期，区分“代码已实现、浏览器已验证、实机已验收”；未做过的测试仍标为待验。
- **仓库自动执行规则：** 根目录 [`AGENTS.md`](../AGENTS.md) 只负责让开发助手自动加载以上约定，不承担第二套文档说明；六份 `docs/` 项目文档结构保持不变。
- **自动一致性检查：** 每次文档或任务关联发生变化后执行 `node scripts/check-docs.mjs`；该脚本检查入口、日期文件、本地链接/锚点、计划与日志任务编号，以及已经填写的 Git SHA 是否真实存在。

日志中新增任务时使用下列追溯表，详细验证可以放在表下的实际验证章节：

| 任务编号 | 当日交付/修改 | 主要文件 | 验证结果及限制 | Git SHA |
| --- | --- | --- | --- | --- |
| `CAR-XXX` | 实际完成内容 | `src/...`、`docs/...` | 运行的命令和实际结果、未覆盖范围 | `未提交` 或真实 SHA |
